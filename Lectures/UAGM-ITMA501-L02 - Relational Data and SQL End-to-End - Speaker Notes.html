Relational Data and SQL, End-to-End

A practical speaking structure for moving from a relational database to an exported, decision-ready SQL result using the Olist Brazilian e-commerce dataset. Power BI reporting continues in L03.

Theory: 120 min Lab: 120 min Break: 15 min Platform: Supabase SQL Editor Dataset: Olist

  • Distribute L02-olist-ingest.sql and an Olist ER diagram through the LMS.

Self-guided setup · Olist ingestion

Upload the nine CSV files to Supabase

Students who miss the live ingestion walkthrough can load Olist through the Supabase Table Editor. The source files are available from the Olist Brazilian E-Commerce page on Kaggle.

  1. Download the Kaggle dataset and extract the ZIP file. Keep the nine files ending in _dataset.csv, plus product_category_name_translation.csv.
  2. Open the Supabase project, select Table Editor, and choose New table or Import data from CSV.
  3. For each CSV, create a table using the filename without .csv as the table name. For example, olist_orders_dataset.csv becomes olist_orders_dataset.
  4. Enable the option that treats the first row as column headers. Keep the delimiter as comma and encoding as UTF-8.
  5. Review the inferred column types before importing. Keep IDs and ZIP prefixes as text; use numeric types for prices, freight, review scores, and counts; use text for raw timestamp columns.
  6. Import one file at a time. Do not rename the columns or tables, because the practice queries depend on the names shown in the ER diagram.
  7. Repeat the process for all nine tables. The geolocation file is much larger than the others and may take longer to import.

Slide 1 · Title3–5 min

Frame SQL as a decision pipeline

Open with the promise: students will begin with an empty database and finish with a report answering a business question. Emphasize that SQL is not isolated syntax; it is the bridge between stored data and decisions.

Ask: “If an e-commerce company wanted to identify its most valuable customers, what information would it need to combine?” Listen for customers, orders, items, prices, and products.

Preview the full path: Supabase stores the tables, SQL selects and combines evidence, CSV carries the result, and Power BI communicates it.

Slide 2 · Agenda5 min

Give students the map

Walk through the session blocks and explain the progression:

  1. Meet the data and understand relational structure.
  2. Write basic queries and summaries.
  3. Combine tables with joins.
  4. Practice 15 queries.
  5. Build an end-to-end report.

Set the expectation that students should type along. The objective is not to watch a polished demo; it is to develop a repeatable workflow.

Slide 3 · Meet Olist10 min

Make the schema concrete before teaching syntax

Introduce Olist as a public-domain Brazilian marketplace dataset with approximately 100,000 orders from 2016–2018. Explain that the nine CSV files represent different business entities and events.

Data location: students can download the dataset from the Olist Brazilian E-Commerce page on Kaggle. The download contains the nine CSV files used in this session.

Show the ER diagram and trace one order from customer to items, products, seller, payment, and review.

Slide 4 · SELECT / WHERE20 min

Teach the query in execution order

Explain that SQL is typed as SELECT ... FROM ... WHERE ..., but the database conceptually starts with FROM, filters with WHERE, and returns columns with SELECT.

SELECT customer_id, customer_city, customer_state
FROM   olist_customers_dataset
WHERE  customer_state = 'SP'
LIMIT  10;

Walk through comparison operators: =, <>, inequalities, IN, BETWEEN, LIKE, and null checks.

Trap: WHERE column = NULL does not find missing values. Use IS NULL or IS NOT NULL.

Live-code a query for São Paulo orders and one for canceled orders. Mention that Olist city values are lowercase and Portuguese, so exact text and case matter.

Check understanding: ask students to predict whether a query using customer_state IN ('SP','RJ','MG') returns rows or errors before running it.
Slide 5 · Aggregates20 min

Move from individual rows to business summaries

Introduce COUNT, SUM, AVG, MIN, and MAX. Connect each function to a business question: how many orders, how much revenue, what average price, and what range?

SELECT c.customer_state,
       SUM(oi.price + oi.freight_value) AS revenue
FROM   olist_order_items_dataset oi
JOIN   olist_orders_dataset o ON oi.order_id = o.order_id
JOIN   olist_customers_dataset c ON o.customer_id = c.customer_id
GROUP BY c.customer_state
ORDER BY revenue DESC
LIMIT 10;

Anchor the rule: every selected column not inside an aggregate must appear in GROUP BY. Then distinguish WHERE, which filters rows before grouping, from HAVING, which filters groups after aggregation.

Ask: “Would you use WHERE or HAVING to keep only states with more than 1,000 orders?” Require students to explain why.
Slide 6 · Relational algebra10 min

Give complex queries a mental model

Present relational algebra as a debugging tool rather than a theory exam:

Projection (π)

Choose columns with SELECT.

Selection (σ)

Choose rows with WHERE.

Join (⋈)

Combine tables on matching keys with JOIN.

Union (∪)

Combine compatible result sets with UNION.

Explain that a five-table query is a composition of small operations. When results are wrong, inspect one layer at a time instead of staring at the whole query.

Slide 7 · JOINs25 min

Make row preservation visible

Draw the four join types and say the defining sentence for each:

  • INNER JOIN: only matching rows from both tables.
  • LEFT JOIN: every row from the left table plus matches from the right.
  • RIGHT JOIN: every row from the right table plus matches from the left.
  • FULL OUTER JOIN: every row from both tables, with nulls where no match exists.

Use row counts to demonstrate the difference. Then build the five-table query one join at a time: orders plus customers, add items, add products, and finally add translated categories.

Common failures: a missing ON clause creates a Cartesian product; unqualified column names become ambiguous; an inner join can unintentionally discard unmatched records.

Explain why the translation table uses LEFT JOIN and why COALESCE preserves a Portuguese category when no English translation exists.

Slide 8–9 · Build and export20 min

Show the SQL pipeline and stop at the CSV

Build the anchor query incrementally and pause after each join to inspect the result. Then demonstrate the export path:

  1. Run the query in the Supabase SQL Editor.
  2. Use the result panel’s Download CSV action.
  3. Save with a descriptive name such as L02-top-customers.csv.
  4. Keep the CSV available for L03.

Tell students that today's target is a reliable handoff from database query to a reusable CSV. L03 will turn that result into a Power BI report.

Bridge: “The query is the analytical work. Next session we will decide how to make its result clear and useful to a reader.”
Lab · Block 0355 min

Coach the 15-query progression

Have students attempt each query before projecting the solution. Keep the progression visible: five basic filters, three operators, four aggregate queries, and three join warmups.

Lab · Block 0460 min

Guide the top-customer SQL result

The business question is: Who are Olist’s top 10 revenue-generating customers, and which product category do they buy most from?

  1. Start with customer revenue, grouping by customer_unique_id, not the per-order customer_id.
  2. Limit that result to the top 10 customers.
  3. Calculate category spend for those customers.
  4. Use ROW_NUMBER() or a simpler second query to select each customer’s top category.
  5. Export the final result as L02-top-customers.csv for the L03 Power BI lab.
Olist gotcha: customer_id identifies a customer record associated with an order; customer_unique_id is the correct field for aggregating the real customer across orders.

For students who struggle with the CTE, provide the two-query fallback. Preserve the business question and the final CSV even if the implementation is simpler.

Close · Debrief15 min

End with a reusable communication pattern

Ask each group to report in this order: question → method → result → limitation → action or next question.

Final bridge: “You can now retrieve decision-ready evidence from connected tables. Next session asks where data comes from and how to assess it before analysis.”

Assign the unfinished queries, one novel business question, and the L03 Power BI preparation.
