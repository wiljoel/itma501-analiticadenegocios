Part 01 · Anatomy of a query

Three keywords. Every query starts here.

SQL is read top-to-bottom, but the database runs it FROM → WHERE → SELECT. Keep that order in your head and everything else clicks.

-- Get 10 São Paulo customers SELECT customer_id, customer_city, customer_state FROM olist_customers_dataset WHERE customer_state = 'SP' LIMIT 10;
Execution order

FROM → WHERE → SELECT

FROM picks the table. WHERE filters rows. SELECT picks columns to return. The order you type is not the order it runs.

Trap: WHERE column = NULL silently returns nothing. Always use IS NULL or IS NOT NULL.
Part 01 · Aggregates

From rows to summaries.

Aggregates reduce many rows to a single value. GROUP BY does it per category. HAVING filters those categories.

-- Revenue per Brazilian state, top 10 SELECT c.customer_state, SUM(oi.price + oi.freight_value) AS revenue FROM olist_order_items_dataset oi JOIN olist_orders_dataset o ON oi.order_id = o.order_id JOIN olist_customers_dataset c ON o.customer_id = c.customer_id GROUP BY c.customer_state ORDER BY revenue DESC LIMIT 10;
Rule

Group everything you don't aggregate.

Every column in SELECT that isn't inside SUM/COUNT/AVG/MIN/MAX must appear in GROUP BY. Postgres will error if you forget.

HAVING vs WHERE: WHERE filters raw rows (before aggregation). HAVING filters aggregated groups (after). HAVING COUNT(*) > 1000 is legal; WHERE COUNT(*) > 1000 is not.
Part 02 · Mental model

Every clause is an operator.

Complex queries aren't monoliths. They're compositions of a handful of simple operations. Learn the algebra, debug faster.

π · Projection

SELECT

Pick which columns to return.

σ · Selection

WHERE

Pick which rows survive.

⋈ · Join

JOIN

Combine two tables on matching keys.

∪ · Union

UNION

Combine result sets, drop duplicates.

Why this matters: a 5-table query is not one thing. It's the composition of several small operations. When it breaks, you know exactly which layer to inspect.
Part 02 · Four joins

Four flavors. Different result sets.

Which rows survive depends on which join you pick. Get it wrong and you either lose data or explode row counts.

INNER JOIN
Only rows that match in BOTH tables.
LEFT JOIN
All rows from the LEFT + matched from right. NULLs where no match.
RIGHT JOIN
Mirror of LEFT. All rows from the RIGHT + matched from left.
FULL OUTER JOIN
All rows from both. NULLs on either side where no match.
Cartesian trap: forget the ON clause and you get every row from A paired with every row from B. On Olist, a JOIN without ON produces ~11 billion rows. Ask me how I know.
Part 02 · Live build

Build a 5-table query, one JOIN at a time.

The final query the class writes today. We add one JOIN at a time so you can see row counts change.

-- Order + customer + item + product + translated category SELECT o.order_id, c.customer_state, oi.price, COALESCE(t.product_category_name_english, p.product_category_name) AS category FROM olist_orders_dataset o JOIN olist_customers_dataset c ON o.customer_id = c.customer_id JOIN olist_order_items_dataset oi ON o.order_id = oi.order_id JOIN olist_products_dataset p ON oi.product_id = p.product_id LEFT JOIN product_category_name_translation t ON p.product_category_name = t.product_category_name;
Why LEFT JOIN on translation? Not every product category has an English translation. An INNER JOIN would drop those rows. LEFT JOIN keeps them, and COALESCE falls back to the Portuguese name.
